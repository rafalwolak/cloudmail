# Cloudmail

[![Deploy to Cloudflare](https://deploy.workers.cloudflare.com/button)](https://deploy.workers.cloudflare.com/?url=https%3A%2F%2Fgithub.com%2Frafalwolak%2Fcloudmail)

An early-stage, self-hosted transactional email service on Cloudflare Workers. This project does not yet provide Resend feature parity. It does not support marketing email.

## Current capabilities

- `POST /emails` accepts `from`, `to`, `subject`, and `text` or `html` with a bearer API key. An optional `Idempotency-Key` prevents duplicate sends for 24 hours. Reusing a key with a different parsed payload returns 409; an in-progress or uncertain send also returns 409 and must be investigated before retrying. The MCP `send_email` tool accepts the same value as `idempotency_key`.
- If `text` is omitted and HTML is supplied, Cloudmail generates a plain-text alternative before sending. An explicitly provided `text`, including an empty string, is preserved. This applies to immediate, batch, template, MCP and scheduled sends; generated text is recorded in history after an attempt.
- `POST /emails/batch` accepts 1-100 transactional messages and validates the whole batch before sending. Messages are processed sequentially; if a send fails, the response includes confirmed IDs and the failed index, and later messages are not attempted. Use an `Idempotency-Key` to prevent repeated batches for 24 hours. An in-progress or uncertain batch cannot be safely retried automatically; inspect history. The `x-batch-validation` header accepts `strict` (the default) or `permissive`; permissive mode sends valid entries and reports validation errors by their original indexes. Sender authorization failures still reject the entire batch.
- Supports one or more `to`, `cc`, and `bcc` recipients (up to 50 total), a single `reply_to` address, custom `headers`, and base64 attachments with optional `content_type` and inline `content_id`. When `content_type` is omitted, Cloudmail infers it from the filename and uses `application/octet-stream` for unknown extensions. Remote attachment URLs are not supported. Unsupported fields are rejected. Other Resend API features are not implemented.
- `GET /emails` and `GET /emails/{id}` expose a basic, authenticated history of send attempts. The history stores sender, primary recipients, subject, creation time, and status. Details expose text and HTML for messages created after content storage was introduced. Bodies are stored in the private R2 bucket without automatic expiration; restrict access and configure an appropriate retention policy. Authentication verification and password reset bodies are excluded. Attachments for messages created after attachment storage was introduced are retained in history; older messages may not have them. `accepted` means accepted by Cloudflare, not delivered. A `pending` or `unknown` status requires investigation before retrying. Listing supports `limit` (1-100) and `before` or `after` cursors, and returns `has_more`, recorded Cc/Bcc/reply-to fields, and `last_event`. The last event is the latest observed recipient event, not a delivery guarantee for every recipient; it is null when no event was recorded.
- `POST /templates`, `GET /templates`, `GET/PATCH/DELETE /templates/{id}`, and `POST /templates/{id}/publish` manage transactional email templates. Draft edits do not affect the last published snapshot. Send with `template: { id, variables }` through the single, batch, or MCP send paths. Variables must be declared as `string` or `number` and use `{{{KEY}}}` placeholders; HTML values are escaped. Avoid using untrusted variables in URL attributes, as HTML escaping does not validate URL schemes. Published templates can also be referenced by a unique alias: use lowercase letters, digits, hyphens or underscores, starting with a letter (up to 64 characters). Alias changes take effect on publication; conflicting published aliases are rejected, and copies do not inherit aliases. The dashboard offers a sandboxed HTML preview of the current draft, including inline styles and embedded data images, with optional example variable values and fallbacks; scripts and external resources are blocked, so it is not a faithful email-client rendering. Rich editing is not yet implemented. Lists support cursor pagination and optional `name` and `status` filters in the API, MCP, and dashboard. Name matching is a case-insensitive literal substring with SQLite ASCII case folding; published status means a published snapshot exists, even if the draft has later edits. Duplication creates an unpublished draft.
- A stateless MCP endpoint at `/mcp` exposes email sending and history tools plus template creation, listing, retrieval, editing, publication, duplication, and deletion over Streamable HTTP, using the same bearer API key as `/emails`.
- Verified administrators can create, list, rename and revoke API keys via `/api/keys`; only a SHA-256 hash is stored, and the token is shown once.
- Better Auth provides email/password authentication backed by D1 and revokes existing sessions on password reset; verification and password-reset messages use the same recorded Cloudmail sending path. Sign-up is disabled by default and requires a verified sending domain.

## Deploy

The Deploy to Cloudflare button provisions a D1 database and uses the `deploy` script to apply migrations before deploying. During setup, configure `BETTER_AUTH_URL` to the exact HTTPS origin of your Worker and provide a unique `BETTER_AUTH_SECRET` with at least 32 bytes of entropy. Authentication stays disabled for the example secret, secrets shorter than 32 characters, or an invalid origin. Length does not prove randomness: generate the secret with a cryptographically secure generator. The button has not yet been verified end to end on a separate account.

For a manual deployment, run `npm ci`, create a D1 database with `npx wrangler d1 create cloudmail-auth`, and replace the placeholder `database_id` and `BETTER_AUTH_URL` in `wrangler.jsonc` with values from your account. Set `BETTER_AUTH_SECRET` using `npx wrangler secret put BETTER_AUTH_SECRET`, then run `npm run deploy`. The optional `API_KEY` secret enables the legacy installation-wide API key. Configure a sending domain in Cloudflare Email Service; account and plan restrictions apply.

To enable registration, set `AUTH_EMAIL_FROM` to an address on your verified sending domain and set `ENABLE_SIGNUP` to `true` in your deployment configuration. Keep registration disabled until you can receive verification emails. Set `ADMIN_EMAIL` to the verified email address of the installation administrator to allow that account to manage API keys. Keys stop working if the configured administrator changes. Keys can have `full_access` or `sending_access`; sending-only keys can call `POST /emails` and `POST /emails/batch`, and use the MCP `send_email` and `send_batch` tools, but cannot access history, template management, or schedule management. Only those sending tools are registered for these MCP connections. The dashboard defaults to sending-only. Existing keys and API-created keys with no permission specified retain full access for compatibility. Sending-only keys can optionally specify `sending_domain` when created in the dashboard. The match is case-insensitive and exact, excluding subdomains. Such keys require a plain ASCII sender mailbox and allow only the `In-Reply-To` and `References` custom headers to support threading without sender overrides; the restriction is enforced after template rendering and before any batch message is sent. The domain must still be onboarded in Cloudflare separately. The dashboard shows which installation settings are missing, but cannot verify DNS or sending-domain readiness. An unverified account can request another verification link from the sign-in screen; this still requires a working sender. Because Cloudflare OAuth currently requires a verified administrator session, the first sending domain must be configured before the initial administrator can verify their email. Authentication endpoints are under `/api/auth`; use `/dashboard` to register (when enabled), sign in, reset a password, manage administrator API keys and templates, and review email attempts and per-recipient delivery events.

Verified administrators can send or schedule transactional email from the dashboard using plain text, HTML, or a published template with variables, plus attachments and To/Cc/Bcc recipients. For templates, the form resolves the published snapshot before confirmation, showing the resulting sender and subject; optional overrides take precedence. The confirmed content is sent as a snapshot, so later template edits do not alter it. The optional Tags editor adds up to 100 name/value pairs using 1-256 ASCII letters, digits, underscores or hyphens per field. Tags are preserved through template preparation and scheduling and can be read under Message content in sent history. The form confirms the recipients and uses an idempotency key for unchanged retries. If the outcome is uncertain, inspect history before sending again; editing the message creates a new request. Cloudflare's complete-message size limits still apply.

Cloudflare dashboard controls allow retrying failed authorization starts, zone discovery and domain loading. If delivery diagnostics return `cloudflare_queue_access_required`, the affected domain offers an explicit reconnect action using the existing authorization flow. Starting that flow requires a click and does not itself grant permissions. After a successful reconnect, choose zones again before retrying diagnostics. The UI also clears this recovery action after a successful recheck.

For local testing, configure `.dev.vars` with `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL=http://127.0.0.1:8787`, and `API_KEY=local-test-key`, apply migrations with `npx wrangler d1 migrations apply cloudmail-auth --local`, start `npm run dev`, and run `npm test` in another terminal. To test registration, add `ENABLE_SIGNUP=true` and `AUTH_EMAIL_FROM` to `.dev.vars`, restart the local server, then run `TEST_SIGNUP=true npm test`. Local email sending is simulated by Wrangler.

For dashboard browser tests, install Chromium once with `npx playwright install chromium`, start the disposable local Worker as above, then run `npm run test:e2e`. Set `BASE_URL` only to the intended local Worker if it uses a different origin. The suite exercises real dashboard assets with synthetic API responses, including an administrator fixture; it does not validate real login or send email. Desktop, mobile and 615px in-app-browser projects run automatically. Failure traces and screenshots are written under `.ai/qa/artifacts_playwright/` and are not committed. See [the dashboard reference review](docs/dashboard-review.md) for scope and limitations.

GitHub Actions runs `npm run check`, `npm test`, and `npm run test:e2e` for pull requests targeting `main` through `.github/workflows/ci.yml`. CI uses Node.js 26 and a disposable local Worker with all D1 migrations applied, generated local credentials, and simulated email sending. D1-backed and cron tests are enabled against the same local state; two profiles cover disabled registration and enabled registration with a verified synthetic administrator. The second profile follows a verification link from the local email simulator, then exercises administrator sessions, sending-only/domain-restricted keys, password reset and session revocation. It does not mark users verified directly in D1 or test real email delivery. No Cloudflare account token or production secrets are needed. The workflow does not configure branch protection. Authentication-profile Worker output is withheld on failure because it can contain verification/reset links; no local mail or credential artifacts are uploaded.

To run the authentication profile locally, use a disposable migrated D1 state directory and start the local Worker with `--var ENABLE_SIGNUP:true --var ADMIN_EMAIL:ci-admin@example.com --var AUTH_EMAIL_FROM:sender@example.com`. Set `TEST_DASHBOARD_ADMIN=ci-admin@example.com`, generate `TEST_DASHBOARD_PASSWORD` in your terminal, and export both variables. Run `node scripts/prepare-local-admin.mjs`, then `TEST_SIGNUP=true TEST_KEYS=true TEST_PASSWORD_RESET=true npm test`. The setup helper accepts only a local HTTP origin, registers the synthetic administrator and follows a newly captured verification link for that email address. It requires a fresh account and does not replace an existing administrator. Keep the same `TEST_BASE_URL`, `TEST_D1_CONFIG` and `TEST_D1_PERSIST` as the local Worker. Normal `npm test` keeps the fixture-dependent scenarios optional.

Never use the API for marketing email: Cloudflare Email Service supports transactional email only.

## Roadmap

Automatic event subscription setup, full message history, complete Resend-compatible domain APIs, expanded MCP coverage, and end-to-end deployment tests remain to be implemented.

Domain management is experimental. A configured Cloudflare OAuth client lets an administrator authorize access, select zones, and enable Email Sending from the dashboard; MCP can inspect selected zones and manage sending domains. The current Cloudmail OAuth client is private and its callback is registered only for the project installation. The one-click workflow is not yet available for independent deployments or other Cloudflare accounts. DNS and delivery readiness are not verified. Full-access keys can use `GET /domains`, `POST /domains`, `GET /domains/{id}`, and `DELETE /domains/{id}` for selected zones. These endpoints expose Cloudflare tags as IDs and report status as `unknown`; they do not yet implement the full Resend contract or verification. The list supports `limit`, `before`, and `after` after fetching all selected zones, and fails if Cloudflare reports an incomplete upstream list. Deleting a sending domain can remove shared DNS records and affect other applications. Changing `BETTER_AUTH_SECRET` makes stored OAuth tokens unreadable and requires reconnecting Cloudflare. The dashboard can disconnect a saved connection by asking Cloudflare to revoke its tokens, then forgetting the selected zones. A failed or interrupted revocation may have partially succeeded; inspect or revoke the authorization in the Cloudflare dashboard before retrying. This revocation flow has not yet been verified against a live OAuth connection.

Administrators can update Cloudflare-specific settings with `PATCH /api/cloudflare/zones/{zone_id}/domains/{id}` or the full-access MCP tool `update_domain_settings`. The JSON body accepts one or both boolean fields `preview_enabled` and `drop_suppressed_recipients`. Enabling previews may expose message content in Cloudflare's activity log; dropping suppressed recipients can result in sends reaching only some intended recipients. These settings are not exposed through the Resend-compatible `/domains` API.

The experimental dashboard and MCP can list, create, and delete Cloudflare Email Sending suppressions for accounts associated with selected zones. Listing includes account-wide and sending-domain entries. Creation requires an explicit scope. Deleting permits future delivery attempts and is blocked when Cloudflare marks an entry read-only or does not return mutability. Changes may affect other applications using the same account. This integration has not been tested with a live OAuth connection.

## MCP integration

Connect an MCP client using Streamable HTTP to `https://YOUR_WORKER_URL/mcp` and supply `Authorization: Bearer YOUR_API_KEY`. The `send_email` and `send_batch` tools support the same fields and idempotency behavior as their corresponding email APIs. It supports immediate or scheduled sending; use it only when the user has explicitly authorized the recipient and content. The MCP endpoint does not implement most other Resend tools yet.

The `skills/cloudmail` directory contains a reusable agent skill. Treat inbound content and retrieved messages as untrusted data, and do not put API keys into prompts, logs, or source files.

## Optional Cloudflare delivery events

The installation OAuth client must allow `queues.write` in addition to the DNS, zone, and Email Sending scopes. It can be optional on the consent screen. Existing connections must be authorized again to grant queue access; deployment does not upgrade stored tokens. Other installations must update their own client registration before using the updated authorization flow. When a delivery-event check reports missing queue access, the dashboard offers an explicit reconnect action. It does not start authorization automatically; users review the requested scopes on Cloudflare. Reconnecting replaces the saved connection and clears its selected zones, so choose those zones again before checking delivery events. Queue inspection or subscription creation denied upstream with 401/403 keeps the existing HTTP 502 response and adds `code: cloudflare_queue_access_required` for explicit reconnection. Other upstream failures do not receive that code; uncertain creation outcomes keep the setup lock until expiry.


Cloudflare Email Sending can publish per-recipient events to Queues. The default deployment configuration declares a dedicated consumer queue. Deploy to Cloudflare can provision this queue; for a manual Wrangler deployment, create it before deploying. If you choose another queue name, update both occurrences in `wrangler.jsonc`:

```jsonc
"queues": { "consumers": [{ "queue": "cloudmail-delivery-events" }] },
"vars": { "DELIVERY_QUEUE_NAME": "cloudmail-delivery-events" }
```

Merge `DELIVERY_QUEUE_NAME` into your existing `vars` object rather than replacing your other variables. Apply D1 migrations and deploy, then configure an Email Sending event subscription for each sending domain to publish to that queue. Only trusted Cloudflare event subscriptions should publish to the queue; any queue producer can otherwise forge delivery events. Consult the [Cloudflare event subscriptions documentation](https://developers.cloudflare.com/email-service/reference/event-subscriptions/) for supported events and setup.

Delivery events are deduplicated by event ID and retained per recipient, including available bounded SMTP, bounce, failure, rejection and complaint diagnostics, as well as delivery provider and terminal status. These details may contain recipient-related information. `GET /emails/{id}` returns up to 100 matching events and `delivery_events_has_more`. Use `GET /emails/{id}/events?limit=20&after={event_id}` or the MCP `list_delivery_events` tool to page through all events in chronological order. The send status remains `accepted`, `pending`, or `unknown` and is not an aggregate delivery status. Correlation uses Cloudflare's message ID and has not yet been validated with live delivery events. Queue failures are retried; configure and monitor a dead-letter queue so exhausted messages can be investigated. Malformed or unsupported events are acknowledged and discarded.

Sent email details include `cc`, `bcc`, and `reply_to` for messages recorded after the recipient-history migration. Earlier messages return `null` for these fields because their values were not stored. These fields may contain sensitive addresses, including blind-copy recipients; full-access API keys and the administrator can read them. Message bodies and new attachments are stored in the private R2 bucket and can be read by full-access keys and administrators. Authentication verification and password reset bodies are excluded. Attachments on new sends are stored in the private bucket and are available to full-access keys and administrators; older messages may not have stored attachments. Content has no automatic expiration, so configure appropriate retention and access controls. Pending scheduled content is available until cancellation or an attempt; canceled messages do not retain their content.

`GET /emails/metrics` and the MCP `get_email_metrics` tool return basic counts over a UTC interval (default last seven days, maximum 366 days). `start_date` is inclusive and `end_date` is exclusive; both accept UTC dates (`YYYY-MM-DD`) or UTC timestamps. Select supported counts with `metrics`, and group by `dimensions=period` with hourly or daily `granularity`. A message-recipient pair appearing in multiple periods is counted once in each period but once in the totals. `sent` counts accepted messages by creation time, while delivery event counts use event time and unique message-recipient pairs. A recipient can appear in more than one event category, and events from the subscribed domains can include messages sent outside Cloudmail. The different units must not be used directly to calculate rates. Results depend on queue subscriptions and retained events; missing events do not prove failed delivery. Other Resend dimensions, filters, rates, and engagement metrics are not implemented. The Metrics dashboard uses the existing daily period data for an interactive metric selector, a chart and a keyboard-scrollable exact-value table. Its 7/30/90-day views use UTC calendar days including the partial current day. Missing buckets display zero recorded observations; they do not establish delivery failure. Interval totals remain separate from daily counts. Chart selection reuses the loaded report without another API call. Reports are cleared on loading, failure and sign-out.

Email requests may include up to 100 `tags`, each with a `name` and `value` containing 1-256 ASCII letters, digits, underscores or hyphens. Tags are stored in email history and exposed by the API and MCP; they are not sent to Cloudflare as headers. Avoid including sensitive data in tags.

Scheduled transactional sends accept `scheduled_at` as an ISO 8601 timestamp or a relative duration such as `in 1 min`, `in 2 hours`, or `in 3 days`, up to 30 days ahead. Relative durations use the server time when the request is first accepted; retries with the same idempotency key and relative expression return the original email ID. `PATCH /emails/{id}` changes the time and `POST /emails/{id}/cancel` cancels an email while it is still scheduled. MCP exposes `reschedule_email` and `cancel_email`; administrators can also reschedule or cancel from the dashboard history. Templates are rendered at scheduling time. Small payloads are stored in D1; payloads over 1.5 MB are stored in the private `INBOUND` R2 bucket under the reserved `scheduled/` prefix. D1 payloads are removed at the attempt or cancellation; R2 cleanup runs on subsequent cron invocations and retries failures. Orphaned objects under that prefix are checked against D1 and removed after at least 24 hours. Protect both stores and avoid scheduling sensitive content unless that storage is appropriate. A minute-based cron processes up to 20 due messages per invocation, so delivery may be delayed by queue volume or platform availability. Failures while preparing a scheduled message before the send call return it to the queue with exponential backoff from one minute up to one hour, so persistent failures do not continuously block other messages. History exposes `preparation_attempts` and `preparation_retry_at` while scheduled; rescheduling clears the backoff. Once the send call starts, failures and interrupted attempts can have an uncertain outcome and are not retried automatically; investigate before retrying. Other natural-language expressions and batch scheduling are not supported.

Full-access API keys can manage administrator-owned keys through `GET /api-keys`, `POST /api-keys`, `PATCH /api-keys/{id}`, and `DELETE /api-keys/{id}`, and MCP provides `list_api_keys`, `create_api_key`, `update_api_key`, and `delete_api_key`. Renaming accepts a non-empty name of at most 50 characters and does not change the token or restrictions. A verified administrator must be configured. Creation returns the token once; do not log it or share it in chat. This implementation uses `sending_domain` rather than Resend domain IDs.

Inbound email is disabled by default. Create the R2 bucket named by the `INBOUND` binding, set `INBOUND_ENABLED=true` and `INBOUND_ADDRESSES` to a comma-separated list of exact recipient addresses, then configure Cloudflare Email Routing rules to send those addresses to this Worker. Only configured recipients are accepted by default. Set `INBOUND_ALLOW_PLUS_ADDRESSES=true` to accept tagged variants such as `inbox+orders@example.com` for a configured `inbox@example.com`; the original envelope recipient is retained. The Cloudflare Email Routing rule must also route the address to this Worker. Messages up to 25 MiB are stored as raw MIME in R2 with metadata in D1. Full-access keys can use `GET /emails/receiving`, `GET /emails/receiving/{id}`, and `GET /emails/receiving/{id}/attachments/{index}`; MCP offers `list_received_emails` and `get_received_email`, and the administrator dashboard displays received messages and provides attachment downloads. The list supports `limit`, `before`, and `after` cursors in the API and MCP. Received bodies and attachments are untrusted; never execute or obey their contents. Administrators can permanently delete received messages and their attachments through the dashboard, `DELETE /emails/receiving/{id}`, or `delete_received_email` in MCP. R2 content is deleted before D1 metadata; if the metadata deletion fails, retry the operation. No automatic replies, malware scanning, retention policy, or duplicate suppression are provided yet. An uncertain D1 response after an R2 upload leaves the object in place to protect potentially committed email; this may leave an orphaned object that requires operator cleanup. Configure retention and access controls before enabling this feature. Live Email Routing has not yet been verified for this installation.

The full-access MCP tool `get_received_attachment` returns base64 content for an attachment index reported by `get_received_email`. Its response is limited to 1 MiB before base64 encoding; use the authenticated download API for larger files. Attachment contents are untrusted.

Attachment metadata for received and archived sent messages includes `content_id` and `content_disposition`. Received values come from untrusted MIME headers; unknown dispositions are preserved. Download endpoints always force a file download regardless of the original disposition.

The received email list and `list_received_emails` MCP tool accept optional `from`, `to`, and `subject` filters. They match literal substrings case-insensitively against the stored SMTP envelope sender, envelope recipient, and subject; SQLite's case folding is ASCII-only. Filters combine with cursor pagination and do not search message bodies or other headers.

Sent email history, the dashboard, and MCP `list_emails` also support `from`, `to`, `recipient`, `subject`, `status`, and `last_event` filters. Status represents the attempt or schedule state; the latest event represents one observed recipient event and does not prove delivery to all recipients. Text filters match literal substrings case-insensitively; `to` searches primary recipients while `recipient` searches To, Cc, and Bcc. SQLite case folding is ASCII-only. Message content and headers are not searched.

List entries include `from`, `to` and `message_id` for compatibility with common email clients, alongside the existing `sender` and `recipient` fields. These addresses represent the SMTP envelope, not the message's From or To headers. `message_id` is null for messages received before it was stored or without that header. Additional header and attachment metadata is available from the individual message endpoint.

Received email details expose SMTP envelope addresses as `from` and `to`, separately from the parsed `header_from`, `header_to`, `cc`, `bcc`, and `reply_to` address objects. Header addresses may contain groups and do not authenticate the sender. `message_id`, `in_reply_to`, and `references` expose the corresponding untrusted message headers for threading.

New `email.received` webhook payloads include the untrusted `message_id` header, bounded to 998 characters, or `null` if absent or received before this field was stored. Previously prepared webhook payloads retain their original contents across retries and replays.

Delivery-event webhooks can be created and listed at `/webhooks`, retrieved or deleted at `/webhooks/{id}`, and managed through MCP or the administrator dashboard. They support `email.sent`, `email.received`, `email.delivered`, `email.deferred`, `email.bounced`, `email.failed`, `email.rejected`, and `email.complained` with delivery events from configured Cloudflare Queue subscriptions; sent and received events are generated locally when acceptance or inbound storage is recorded. The Resend-compatible `email.delivery_delayed` event is also available for Cloudflare deferred events. If both delayed names are selected, one event is sent using `email.delivery_delayed`. A signing secret is returned only on creation; store it securely. Requests use `svix-id`, `svix-timestamp`, and `svix-signature` HMAC-SHA256 headers over `id.timestamp.raw_body`. Delivery is at least once: deduplicate using `svix-id`. Retries use exponential backoff for up to eight attempts. Redirects are not followed. A minute cron handles up to 20 deliveries per run; backlog and Cloudflare availability may delay delivery. The secret is stored in D1, so protect database access. Inspect delivery states with `GET /webhooks/{id}/deliveries` or MCP `list_webhook_deliveries`; pagination accepts `limit` and `after`. Individual attempts are available through `GET /webhooks/{id}/deliveries/{delivery_id}/attempts`, MCP `list_webhook_attempts`, and the dashboard. Resend-style inspection is also available at `GET /webhooks/{id}/events`, `GET /webhooks/{id}/events/{event_id}`, and `GET /webhooks/{id}/events/{event_id}/attempts`; response bodies are retained up to 4096 bytes and can contain sensitive data; older attempts may have no response. A delivery stores its prepared payload in D1 before its first attempt; retries and replays use that same payload. Inspect it with `GET /webhooks/{id}/deliveries/{delivery_id}`, MCP `get_webhook_delivery`, or the dashboard. It can contain recipient information and is null before preparation or for older deliveries. New webhook payloads include the original email creation time and represent tags as an object keyed by tag name; if names repeat, the last value wins. Previously saved payloads retain their original format for retries and replays. A saved payload alone does not prove that a request was sent. Attempts recorded before this feature are unavailable. Response bodies are untrusted and may be truncated. Replay an existing delivery with `POST /webhooks/{id}/deliveries/{delivery_id}/replay`, MCP `replay_webhook_delivery`, or the dashboard. A replay has a new delivery ID and does not alter existing automatic retries. The Resend-style `POST /webhooks/{id}/events/{event_id}/replay` instead requeues the same completed event ID for one attempt, preserves its payload and history, and rejects concurrent pending or active deliveries. A worker interruption may cause another attempt after the lease expires. Update endpoints, events, and `status` (`enabled` or `disabled`) with `PATCH /webhooks/{id}`. Disabling pauses pending deliveries and skips new events; in-flight requests may finish, and paused deliveries resume when enabled. Rotate secrets with `POST /webhooks/{id}/rotate-secret`, or use the dashboard and MCP. Both old and new secrets sign requests for 24 hours after rotation; a second rotation is blocked during that period. In-flight requests may already use the previous endpoint or secret. A sent event means Cloudflare accepted the message, not that it was delivered. Received events contain metadata only, not the message body. Deleting an inbound email also removes its associated webhook deliveries. Delivery event subscriptions must be configured separately and have not been verified with real messages.

Sent email details include attachment metadata when retained. Download a file with `GET /emails/{id}/attachments/{index}` using a full-access key, or use the administrator dashboard. Downloads are served as attachments without inline rendering. Scheduled messages expose attachments before an attempt and after archiving; cancellation removes access to their content. Existing messages and authentication emails may not contain archived attachments. The private R2 objects have no automatic expiration.

Cancellation schedules removal of any pre-send archive, even if its database flag was not saved. The minute cron retries cleanup after storage or database failures; deletion is asynchronous and may be delayed by backlog or service availability.

The `get_sent_attachment` MCP tool returns an archived attachment as base64 to full-access clients, with a 1 MiB limit. Use the authenticated download API for larger files. Treat file contents as untrusted.

Full-access clients can list attachment metadata at `GET /emails/{id}/attachments` and `GET /emails/receiving/{id}/attachments`, or with MCP `list_sent_attachments` and `list_received_attachments`. Lists support `limit`, `before`, and `after`; cursors are zero-based attachment indexes. The download endpoint requires authentication and returns file bytes rather than a temporary public URL, so this is not the complete Resend attachment contract. Older sent messages without retained attachment metadata return 404.

MCP discovery is available without authentication through `/.well-known/ai-catalog.json` and `/mcp/server-card`. The card points to the configured `BETTER_AUTH_URL` origin and describes the required Bearer API key; it does not provide OAuth login. Treat discovery metadata as advisory and verify the endpoint before supplying credentials.
