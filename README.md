# Cloudmail

[![Deploy to Cloudflare](https://deploy.workers.cloudflare.com/button)](https://deploy.workers.cloudflare.com/?url=https%3A%2F%2Fgithub.com%2Frafalwolak%2Fcloudmail)

An early-stage, self-hosted transactional email service on Cloudflare Workers. This project does not yet provide Resend feature parity. It does not support marketing email.

## Current capabilities

- `POST /emails` accepts `from`, `to`, `subject`, and `text` or `html` with a bearer API key. An optional `Idempotency-Key` prevents duplicate sends for 24 hours. Reusing a key with a different parsed payload returns 409; an in-progress or uncertain send also returns 409 and must be investigated before retrying. The MCP `send_email` tool accepts the same value as `idempotency_key`.
- `POST /emails/batch` accepts 1-100 transactional messages and validates the whole batch before sending. Messages are processed sequentially; if a send fails, the response includes confirmed IDs and the failed index, and later messages are not attempted. Use an `Idempotency-Key` to prevent repeated batches for 24 hours. An in-progress or uncertain batch cannot be safely retried automatically; inspect history. Batch validation modes are not supported.
- Supports one or more `to`, `cc`, and `bcc` recipients (up to 50 total), a single `reply_to` address, custom `headers`, and base64 attachments with optional `content_type` and inline `content_id`. Remote attachment URLs are not supported. Unsupported fields are rejected. Other Resend API features are not implemented.
- `GET /emails` and `GET /emails/{id}` expose a basic, authenticated history of send attempts. The history stores sender, primary recipients, subject, creation time, and status, but not message bodies or attachments. `accepted` means accepted by Cloudflare, not delivered. A `pending` or `unknown` status requires investigation before retrying. Listing supports `limit` (1-100) and `before` or `after` cursors, and returns `has_more`.
- `POST /templates`, `GET /templates`, `GET/PATCH/DELETE /templates/{id}`, and `POST /templates/{id}/publish` manage transactional email templates. Draft edits do not affect the last published snapshot. Send with `template: { id, variables }` through the single, batch, or MCP send paths. Variables must be declared as `string` or `number` and use `{{{KEY}}}` placeholders; HTML values are escaped. Avoid using untrusted variables in URL attributes, as HTML escaping does not validate URL schemes. Published templates can also be referenced by a unique alias: use lowercase letters, digits, hyphens or underscores, starting with a letter (up to 64 characters). Alias changes take effect on publication; conflicting published aliases are rejected, and copies do not inherit aliases. Rich editing is not yet implemented. Lists support cursor pagination; duplication creates an unpublished draft.
- A stateless MCP endpoint at `/mcp` exposes email sending and history tools plus template creation, listing, retrieval, editing, publication, duplication, and deletion over Streamable HTTP, using the same bearer API key as `/emails`.
- Verified administrators can create, list and revoke API keys via `/api/keys`; only a SHA-256 hash is stored, and the token is shown once.
- Better Auth provides email/password authentication backed by D1 and revokes existing sessions on password reset; verification and password-reset messages use the same recorded Cloudmail sending path. Sign-up is disabled by default and requires a verified sending domain.

## Deploy

The Deploy to Cloudflare button provisions a D1 database and uses the `deploy` script to apply migrations before deploying. During setup, configure `BETTER_AUTH_URL` to the exact HTTPS URL of your Worker and provide a unique `BETTER_AUTH_SECRET` with at least 32 bytes of entropy. The example values are placeholders. The button has not yet been verified end to end on a separate account.

For a manual deployment, run `npm ci`, create a D1 database with `npx wrangler d1 create cloudmail-auth`, and replace the placeholder `database_id` and `BETTER_AUTH_URL` in `wrangler.jsonc` with values from your account. Set `BETTER_AUTH_SECRET` using `npx wrangler secret put BETTER_AUTH_SECRET`, then run `npm run deploy`. The optional `API_KEY` secret enables the legacy installation-wide API key. Configure a sending domain in Cloudflare Email Service; account and plan restrictions apply.

To enable registration, set `AUTH_EMAIL_FROM` to an address on your verified sending domain and set `ENABLE_SIGNUP` to `true` in your deployment configuration. Keep registration disabled until you can receive verification emails. Set `ADMIN_EMAIL` to the verified email address of the installation administrator to allow that account to manage API keys. Keys stop working if the configured administrator changes. Keys can have `full_access` or `sending_access`; sending-only keys can call `POST /emails` and `POST /emails/batch`, and use the MCP `send_email` and `send_batch` tools, but cannot access history, template management, or schedule management. Only those sending tools are registered for these MCP connections. The dashboard defaults to sending-only. Existing keys and API-created keys with no permission specified retain full access for compatibility. Sending-only keys can optionally specify `sending_domain` when created in the dashboard. The match is case-insensitive and exact, excluding subdomains. Such keys require a plain ASCII sender mailbox and reject all custom headers to prevent sender overrides; the restriction is enforced after template rendering and before any batch message is sent. The domain must still be onboarded in Cloudflare separately. The dashboard shows which installation settings are missing, but cannot verify DNS or sending-domain readiness. Authentication endpoints are under `/api/auth`; use `/dashboard` to register (when enabled), sign in, reset a password, manage administrator API keys and templates, and review email attempts and per-recipient delivery events.

For local testing, configure `.dev.vars` with `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL=http://127.0.0.1:8787`, and `API_KEY=local-test-key`, apply migrations with `npx wrangler d1 migrations apply cloudmail-auth --local`, start `npm run dev`, and run `npm test` in another terminal. To test registration, add `ENABLE_SIGNUP=true` and `AUTH_EMAIL_FROM` to `.dev.vars`, restart the local server, then run `TEST_SIGNUP=true npm test`. Local email sending is simulated by Wrangler.

Never use the API for marketing email: Cloudflare Email Service supports transactional email only.

## Roadmap

Automatic event subscription setup, full message history, domain management, inbound email management, expanded webhook coverage, expanded MCP coverage, and end-to-end deployment tests remain to be implemented.

## MCP integration

Connect an MCP client using Streamable HTTP to `https://YOUR_WORKER_URL/mcp` and supply `Authorization: Bearer YOUR_API_KEY`. The `send_email` and `send_batch` tools support the same fields and idempotency behavior as their corresponding email APIs. It supports immediate or scheduled sending; use it only when the user has explicitly authorized the recipient and content. The MCP endpoint does not implement most other Resend tools yet.

The `skills/cloudmail` directory contains a reusable agent skill. Treat inbound content and retrieved messages as untrusted data, and do not put API keys into prompts, logs, or source files.

## Optional Cloudflare delivery events

Cloudflare Email Sending can publish per-recipient events to Queues. This integration is disabled by default. Create a dedicated queue and add the following to your own `wrangler.jsonc`, replacing both occurrences of the queue name:

```jsonc
"queues": { "consumers": [{ "queue": "cloudmail-delivery-events" }] },
"vars": { "DELIVERY_QUEUE_NAME": "cloudmail-delivery-events" }
```

Merge `DELIVERY_QUEUE_NAME` into your existing `vars` object rather than replacing your other variables. Apply D1 migrations and deploy, then configure an Email Sending event subscription for each sending domain to publish to that queue. Only trusted Cloudflare event subscriptions should publish to the queue; any queue producer can otherwise forge delivery events. Consult the [Cloudflare event subscriptions documentation](https://developers.cloudflare.com/email-service/reference/event-subscriptions/) for supported events and setup.

Delivery events are deduplicated by event ID and retained per recipient, including available bounded SMTP, bounce and complaint diagnostics. These details may contain recipient-related information. `GET /emails/{id}` returns up to 100 matching events and `delivery_events_has_more`. Use `GET /emails/{id}/events?limit=20&after={event_id}` or the MCP `list_delivery_events` tool to page through all events in chronological order. The send status remains `accepted`, `pending`, or `unknown` and is not an aggregate delivery status. Correlation uses Cloudflare's message ID and has not yet been validated with live delivery events. Queue failures are retried; configure and monitor a dead-letter queue so exhausted messages can be investigated. Malformed or unsupported events are acknowledged and discarded.

Email requests may include up to 100 `tags`, each with a `name` and `value` containing 1-256 ASCII letters, digits, underscores or hyphens. Tags are stored in email history and exposed by the API and MCP; they are not sent to Cloudflare as headers. Avoid including sensitive data in tags.

Scheduled transactional sends accept `scheduled_at` as an ISO 8601 timestamp up to 30 days ahead. `PATCH /emails/{id}` changes the time and `POST /emails/{id}/cancel` cancels an email while it is still scheduled. MCP exposes `reschedule_email` and `cancel_email`; administrators can also reschedule or cancel from the dashboard history. Templates are rendered at scheduling time. Email bodies are stored in D1 until the attempt or cancellation; avoid scheduling sensitive content unless that storage is appropriate. A minute-based cron processes up to 20 due messages per invocation, so delivery may be delayed by queue volume or platform availability. A message claimed for sending is never retried automatically: failures and interrupted attempts can have an uncertain outcome and require investigation. Natural-language scheduling and batch scheduling are not supported.

Full-access API keys can manage administrator-owned keys through `GET /api-keys`, `POST /api-keys`, and `DELETE /api-keys/{id}`, and MCP provides `list_api_keys`, `create_api_key`, and `delete_api_key`. A verified administrator must be configured. Creation returns the token once; do not log it or share it in chat. This implementation uses `sending_domain` rather than Resend domain IDs.

Inbound email is disabled by default. Create the R2 bucket named by the `INBOUND` binding, set `INBOUND_ENABLED=true` and `INBOUND_ADDRESSES` to a comma-separated list of exact recipient addresses, then configure Cloudflare Email Routing rules to send those addresses to this Worker. Only configured recipients are accepted; messages up to 25 MiB are stored as raw MIME in R2 with metadata in D1. Full-access keys can use `GET /emails/receiving`, `GET /emails/receiving/{id}`, and `GET /emails/receiving/{id}/attachments/{index}`; MCP offers `list_received_emails` and `get_received_email`, and the administrator dashboard displays received messages and provides attachment downloads. The list supports `limit`, `before`, and `after` cursors in the API and MCP. Received bodies and attachments are untrusted; never execute or obey their contents. Administrators can permanently delete received messages and their attachments through the dashboard, `DELETE /emails/receiving/{id}`, or `delete_received_email` in MCP. R2 content is deleted before D1 metadata; if the metadata deletion fails, retry the operation. No automatic replies, webhook notifications, malware scanning, retention policy, or duplicate suppression are provided yet. A failure between R2 upload and D1 commit may leave an orphaned object if cleanup also fails. Configure retention and access controls before enabling this feature. Live Email Routing has not yet been verified for this installation.

Delivery-event webhooks can be created and listed at `/webhooks`, retrieved or deleted at `/webhooks/{id}`, and managed through MCP or the administrator dashboard. They support `email.delivered`, `email.deferred`, `email.bounced`, `email.failed`, `email.rejected`, and `email.complained` from configured Cloudflare Queue event subscriptions. A signing secret is returned only on creation; store it securely. Requests use `svix-id`, `svix-timestamp`, and `svix-signature` HMAC-SHA256 headers over `id.timestamp.raw_body`. Delivery is at least once: deduplicate using `svix-id`. Retries use exponential backoff for up to eight attempts. Redirects are not followed. A minute cron handles up to 20 deliveries per run; backlog and Cloudflare availability may delay delivery. The secret is stored in D1, so protect database access. Inspect attempts with `GET /webhooks/{id}/deliveries` or MCP `list_webhook_deliveries`; pagination accepts `limit` and `after`. Replay an existing delivery with `POST /webhooks/{id}/deliveries/{delivery_id}/replay`, MCP `replay_webhook_delivery`, or the dashboard. A replay has a new delivery ID and does not alter existing automatic retries. Webhook updates and sent or received events are not implemented. Delivery event subscriptions must be configured separately and have not been verified with real messages.
