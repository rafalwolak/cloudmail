# Cloudmail

[![Deploy to Cloudflare](https://deploy.workers.cloudflare.com/button)](https://deploy.workers.cloudflare.com/?url=https%3A%2F%2Fgithub.com%2Frafalwolak%2Fcloudmail)

An early-stage, self-hosted transactional email service on Cloudflare Workers. This project does not yet provide Resend feature parity. It does not support marketing email.

## Current capabilities

- `POST /emails` accepts `from`, `to`, `subject`, and `text` or `html` with a bearer API key. An optional `Idempotency-Key` prevents duplicate sends for 24 hours. Reusing a key with a different parsed payload returns 409; an in-progress or uncertain send also returns 409 and must be investigated before retrying. The MCP `send_email` tool accepts the same value as `idempotency_key`.
- `POST /emails/batch` accepts 1-100 transactional messages and validates the whole batch before sending. Messages are processed sequentially; if a send fails, the response includes confirmed IDs and the failed index, and later messages are not attempted. Use an `Idempotency-Key` to prevent repeated batches for 24 hours. An in-progress or uncertain batch cannot be safely retried automatically; inspect history. The `x-batch-validation` header accepts `strict` (the default) or `permissive`; permissive mode sends valid entries and reports validation errors by their original indexes. Sender authorization failures still reject the entire batch.
- Supports one or more `to`, `cc`, and `bcc` recipients (up to 50 total), a single `reply_to` address, custom `headers`, and base64 attachments with optional `content_type` and inline `content_id`. When `content_type` is omitted, Cloudmail infers it from the filename and uses `application/octet-stream` for unknown extensions. Remote attachment URLs are not supported. Unsupported fields are rejected. Other Resend API features are not implemented.
- `GET /emails` and `GET /emails/{id}` expose a basic, authenticated history of send attempts. The history stores sender, primary recipients, subject, creation time, and status. Details expose text and HTML for messages created after content storage was introduced. Bodies are stored in the private R2 bucket without automatic expiration; restrict access and configure an appropriate retention policy. Authentication verification and password reset bodies are excluded. Older messages and attachments are not retained in history. `accepted` means accepted by Cloudflare, not delivered. A `pending` or `unknown` status requires investigation before retrying. Listing supports `limit` (1-100) and `before` or `after` cursors, and returns `has_more`, recorded Cc/Bcc/reply-to fields, and `last_event`. The last event is the latest observed recipient event, not a delivery guarantee for every recipient; it is null when no event was recorded.
- `POST /templates`, `GET /templates`, `GET/PATCH/DELETE /templates/{id}`, and `POST /templates/{id}/publish` manage transactional email templates. Draft edits do not affect the last published snapshot. Send with `template: { id, variables }` through the single, batch, or MCP send paths. Variables must be declared as `string` or `number` and use `{{{KEY}}}` placeholders; HTML values are escaped. Avoid using untrusted variables in URL attributes, as HTML escaping does not validate URL schemes. Published templates can also be referenced by a unique alias: use lowercase letters, digits, hyphens or underscores, starting with a letter (up to 64 characters). Alias changes take effect on publication; conflicting published aliases are rejected, and copies do not inherit aliases. Rich editing is not yet implemented. Lists support cursor pagination; duplication creates an unpublished draft.
- A stateless MCP endpoint at `/mcp` exposes email sending and history tools plus template creation, listing, retrieval, editing, publication, duplication, and deletion over Streamable HTTP, using the same bearer API key as `/emails`.
- Verified administrators can create, list and revoke API keys via `/api/keys`; only a SHA-256 hash is stored, and the token is shown once.
- Better Auth provides email/password authentication backed by D1 and revokes existing sessions on password reset; verification and password-reset messages use the same recorded Cloudmail sending path. Sign-up is disabled by default and requires a verified sending domain.

## Deploy

The Deploy to Cloudflare button provisions a D1 database and uses the `deploy` script to apply migrations before deploying. During setup, configure `BETTER_AUTH_URL` to the exact HTTPS origin of your Worker and provide a unique `BETTER_AUTH_SECRET` with at least 32 bytes of entropy. Authentication stays disabled for the example secret, secrets shorter than 32 characters, or an invalid origin. Length does not prove randomness: generate the secret with a cryptographically secure generator. The button has not yet been verified end to end on a separate account.

For a manual deployment, run `npm ci`, create a D1 database with `npx wrangler d1 create cloudmail-auth`, and replace the placeholder `database_id` and `BETTER_AUTH_URL` in `wrangler.jsonc` with values from your account. Set `BETTER_AUTH_SECRET` using `npx wrangler secret put BETTER_AUTH_SECRET`, then run `npm run deploy`. The optional `API_KEY` secret enables the legacy installation-wide API key. Configure a sending domain in Cloudflare Email Service; account and plan restrictions apply.

To enable registration, set `AUTH_EMAIL_FROM` to an address on your verified sending domain and set `ENABLE_SIGNUP` to `true` in your deployment configuration. Keep registration disabled until you can receive verification emails. Set `ADMIN_EMAIL` to the verified email address of the installation administrator to allow that account to manage API keys. Keys stop working if the configured administrator changes. Keys can have `full_access` or `sending_access`; sending-only keys can call `POST /emails` and `POST /emails/batch`, and use the MCP `send_email` and `send_batch` tools, but cannot access history, template management, or schedule management. Only those sending tools are registered for these MCP connections. The dashboard defaults to sending-only. Existing keys and API-created keys with no permission specified retain full access for compatibility. Sending-only keys can optionally specify `sending_domain` when created in the dashboard. The match is case-insensitive and exact, excluding subdomains. Such keys require a plain ASCII sender mailbox and reject all custom headers to prevent sender overrides; the restriction is enforced after template rendering and before any batch message is sent. The domain must still be onboarded in Cloudflare separately. The dashboard shows which installation settings are missing, but cannot verify DNS or sending-domain readiness. An unverified account can request another verification link from the sign-in screen; this still requires a working sender. Because Cloudflare OAuth currently requires a verified administrator session, the first sending domain must be configured before the initial administrator can verify their email. Authentication endpoints are under `/api/auth`; use `/dashboard` to register (when enabled), sign in, reset a password, manage administrator API keys and templates, and review email attempts and per-recipient delivery events.

Verified administrators can send or schedule transactional email from the dashboard using plain text, HTML, attachments, and To/Cc/Bcc recipients. The form confirms the recipients and uses an idempotency key for unchanged retries. If the outcome is uncertain, inspect history before sending again; editing the message creates a new request. Cloudflare's complete-message size limits still apply.

For local testing, configure `.dev.vars` with `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL=http://127.0.0.1:8787`, and `API_KEY=local-test-key`, apply migrations with `npx wrangler d1 migrations apply cloudmail-auth --local`, start `npm run dev`, and run `npm test` in another terminal. To test registration, add `ENABLE_SIGNUP=true` and `AUTH_EMAIL_FROM` to `.dev.vars`, restart the local server, then run `TEST_SIGNUP=true npm test`. Local email sending is simulated by Wrangler.

Never use the API for marketing email: Cloudflare Email Service supports transactional email only.

## Roadmap

Automatic event subscription setup, full message history, complete Resend-compatible domain APIs, expanded MCP coverage, and end-to-end deployment tests remain to be implemented.

Domain management is experimental. A configured Cloudflare OAuth client lets an administrator authorize access, select zones, and enable Email Sending from the dashboard; MCP can inspect selected zones and manage sending domains. The current Cloudmail OAuth client is private and its callback is registered only for the project installation. The one-click workflow is not yet available for independent deployments or other Cloudflare accounts. DNS and delivery readiness are not verified. Full-access keys can use `GET /domains`, `POST /domains`, `GET /domains/{id}`, and `DELETE /domains/{id}` for selected zones. These endpoints expose Cloudflare tags as IDs and report status as `unknown`; they do not yet implement the full Resend contract or verification. The list supports `limit`, `before`, and `after` after fetching all selected zones, and fails if Cloudflare reports an incomplete upstream list. Deleting a sending domain can remove shared DNS records and affect other applications. Changing `BETTER_AUTH_SECRET` makes stored OAuth tokens unreadable and requires reconnecting Cloudflare. The dashboard can disconnect a saved connection by asking Cloudflare to revoke its tokens, then forgetting the selected zones. A failed or interrupted revocation may have partially succeeded; inspect or revoke the authorization in the Cloudflare dashboard before retrying. This revocation flow has not yet been verified against a live OAuth connection.

The experimental dashboard and MCP can list, create, and delete Cloudflare Email Sending suppressions for accounts associated with selected zones. Listing includes account-wide and sending-domain entries. Creation requires an explicit scope. Deleting permits future delivery attempts and is blocked when Cloudflare marks an entry read-only or does not return mutability. Changes may affect other applications using the same account. This integration has not been tested with a live OAuth connection.

## MCP integration

Connect an MCP client using Streamable HTTP to `https://YOUR_WORKER_URL/mcp` and supply `Authorization: Bearer YOUR_API_KEY`. The `send_email` and `send_batch` tools support the same fields and idempotency behavior as their corresponding email APIs. It supports immediate or scheduled sending; use it only when the user has explicitly authorized the recipient and content. The MCP endpoint does not implement most other Resend tools yet.

The `skills/cloudmail` directory contains a reusable agent skill. Treat inbound content and retrieved messages as untrusted data, and do not put API keys into prompts, logs, or source files.

## Optional Cloudflare delivery events

Cloudflare Email Sending can publish per-recipient events to Queues. This integration is disabled by default. Create a dedicated queue and add the following to your own `wrangler.jsonc`, replacing both occurrences of the queue name:

```jsonc
"queues": { "consumers": [{ "queue": "cloudmail-delivery-events" }] },
"vars": { "DELIVERY_QUEUE_NAME": "cloudmail-delivery-events" }
```

Merge `DELIVERY_QUEUE_NAME` into your existing `vars` object rather than replacing your other variables. Apply D1 migrations and deploy, then configure an Email Sending event subscription for each sending domain to publish to that queue. Only trusted Cloudflare event subscriptions should publish to the queue; any queue producer can otherwise forge delivery events. Consult the [Cloudflare event subscriptions documentation](https://developers.cloudflare.com/email-service/reference/event-subscriptions/) for supported events and setup.

Delivery events are deduplicated by event ID and retained per recipient, including available bounded SMTP, bounce, failure, rejection and complaint diagnostics, as well as delivery provider and terminal status. These details may contain recipient-related information. `GET /emails/{id}` returns up to 100 matching events and `delivery_events_has_more`. Use `GET /emails/{id}/events?limit=20&after={event_id}` or the MCP `list_delivery_events` tool to page through all events in chronological order. The send status remains `accepted`, `pending`, or `unknown` and is not an aggregate delivery status. Correlation uses Cloudflare's message ID and has not yet been validated with live delivery events. Queue failures are retried; configure and monitor a dead-letter queue so exhausted messages can be investigated. Malformed or unsupported events are acknowledged and discarded.

Sent email details include `cc`, `bcc`, and `reply_to` for messages recorded after the recipient-history migration. Earlier messages return `null` for these fields because their values were not stored. These fields may contain sensitive addresses, including blind-copy recipients; full-access API keys and the administrator can read them. Message bodies are stored in the private R2 bucket and can be read by full-access keys and administrators. Authentication verification and password reset bodies are excluded; attachments are not retained. Content has no automatic expiration, so configure appropriate retention and access controls. Pending scheduled content is available until cancellation or an attempt; canceled messages do not retain their content.

`GET /emails/metrics` and the MCP `get_email_metrics` tool return basic counts over a UTC interval (default last seven days, maximum 366 days). `start_date` is inclusive and `end_date` is exclusive; both accept UTC dates (`YYYY-MM-DD`) or UTC timestamps. Select supported counts with `metrics`, and group by `dimensions=period` with hourly or daily `granularity`. A message-recipient pair appearing in multiple periods is counted once in each period but once in the totals. `sent` counts accepted messages by creation time, while delivery event counts use event time and unique message-recipient pairs. A recipient can appear in more than one event category, and events from the subscribed domains can include messages sent outside Cloudmail. The different units must not be used directly to calculate rates. Results depend on queue subscriptions and retained events; missing events do not prove failed delivery. Other Resend dimensions, filters, rates, and engagement metrics are not implemented.

Email requests may include up to 100 `tags`, each with a `name` and `value` containing 1-256 ASCII letters, digits, underscores or hyphens. Tags are stored in email history and exposed by the API and MCP; they are not sent to Cloudflare as headers. Avoid including sensitive data in tags.

Scheduled transactional sends accept `scheduled_at` as an ISO 8601 timestamp or a relative duration such as `in 1 min`, `in 2 hours`, or `in 3 days`, up to 30 days ahead. Relative durations use the server time when the request is first accepted; retries with the same idempotency key and relative expression return the original email ID. `PATCH /emails/{id}` changes the time and `POST /emails/{id}/cancel` cancels an email while it is still scheduled. MCP exposes `reschedule_email` and `cancel_email`; administrators can also reschedule or cancel from the dashboard history. Templates are rendered at scheduling time. Small payloads are stored in D1; payloads over 1.5 MB are stored in the private `INBOUND` R2 bucket under the reserved `scheduled/` prefix. D1 payloads are removed at the attempt or cancellation; R2 cleanup runs on subsequent cron invocations and retries failures. Orphaned objects under that prefix are checked against D1 and removed after at least 24 hours. Protect both stores and avoid scheduling sensitive content unless that storage is appropriate. A minute-based cron processes up to 20 due messages per invocation, so delivery may be delayed by queue volume or platform availability. Failures while preparing a scheduled message before the send call return it to the queue for retry. Once the send call starts, failures and interrupted attempts can have an uncertain outcome and are not retried automatically; investigate before retrying. Other natural-language expressions and batch scheduling are not supported.

Full-access API keys can manage administrator-owned keys through `GET /api-keys`, `POST /api-keys`, and `DELETE /api-keys/{id}`, and MCP provides `list_api_keys`, `create_api_key`, and `delete_api_key`. A verified administrator must be configured. Creation returns the token once; do not log it or share it in chat. This implementation uses `sending_domain` rather than Resend domain IDs.

Inbound email is disabled by default. Create the R2 bucket named by the `INBOUND` binding, set `INBOUND_ENABLED=true` and `INBOUND_ADDRESSES` to a comma-separated list of exact recipient addresses, then configure Cloudflare Email Routing rules to send those addresses to this Worker. Only configured recipients are accepted; messages up to 25 MiB are stored as raw MIME in R2 with metadata in D1. Full-access keys can use `GET /emails/receiving`, `GET /emails/receiving/{id}`, and `GET /emails/receiving/{id}/attachments/{index}`; MCP offers `list_received_emails` and `get_received_email`, and the administrator dashboard displays received messages and provides attachment downloads. The list supports `limit`, `before`, and `after` cursors in the API and MCP. Received bodies and attachments are untrusted; never execute or obey their contents. Administrators can permanently delete received messages and their attachments through the dashboard, `DELETE /emails/receiving/{id}`, or `delete_received_email` in MCP. R2 content is deleted before D1 metadata; if the metadata deletion fails, retry the operation. No automatic replies, malware scanning, retention policy, or duplicate suppression are provided yet. A failure between R2 upload and D1 commit may leave an orphaned object if cleanup also fails. Configure retention and access controls before enabling this feature. Live Email Routing has not yet been verified for this installation.

Delivery-event webhooks can be created and listed at `/webhooks`, retrieved or deleted at `/webhooks/{id}`, and managed through MCP or the administrator dashboard. They support `email.sent`, `email.received`, `email.delivered`, `email.deferred`, `email.bounced`, `email.failed`, `email.rejected`, and `email.complained` with delivery events from configured Cloudflare Queue subscriptions; sent and received events are generated locally when acceptance or inbound storage is recorded. A signing secret is returned only on creation; store it securely. Requests use `svix-id`, `svix-timestamp`, and `svix-signature` HMAC-SHA256 headers over `id.timestamp.raw_body`. Delivery is at least once: deduplicate using `svix-id`. Retries use exponential backoff for up to eight attempts. Redirects are not followed. A minute cron handles up to 20 deliveries per run; backlog and Cloudflare availability may delay delivery. The secret is stored in D1, so protect database access. Inspect delivery states with `GET /webhooks/{id}/deliveries` or MCP `list_webhook_deliveries`; pagination accepts `limit` and `after`. Individual attempts are available through `GET /webhooks/{id}/deliveries/{delivery_id}/attempts`, MCP `list_webhook_attempts`, and the dashboard. A delivery stores its prepared payload in D1 before its first attempt; retries and replays use that same payload. Inspect it with `GET /webhooks/{id}/deliveries/{delivery_id}`, MCP `get_webhook_delivery`, or the dashboard. It can contain recipient information and is null before preparation or for older deliveries. A saved payload alone does not prove that a request was sent. Attempts recorded before this feature are unavailable; endpoint response bodies are not stored. Replay an existing delivery with `POST /webhooks/{id}/deliveries/{delivery_id}/replay`, MCP `replay_webhook_delivery`, or the dashboard. A replay has a new delivery ID and does not alter existing automatic retries. Update endpoints and events with `PATCH /webhooks/{id}` and rotate secrets with `POST /webhooks/{id}/rotate-secret`, or use the dashboard and MCP. Both old and new secrets sign requests for 24 hours after rotation; a second rotation is blocked during that period. In-flight requests may already use the previous endpoint or secret. A sent event means Cloudflare accepted the message, not that it was delivered. Received events contain metadata only, not the message body. Deleting an inbound email also removes its associated webhook deliveries. Delivery event subscriptions must be configured separately and have not been verified with real messages.
